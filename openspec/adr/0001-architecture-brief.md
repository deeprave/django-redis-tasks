# ADR 0001: Architecture Brief for Redis-Backed Django Tasks

## Status

Accepted

## Context

`django-redis-tasks` was built against the external `django_tasks` package and
also contains its own local queue polling loop. Django 6 provides `django.tasks`
as the public task-definition, enqueueing, and result API, but deliberately does
not provide a production worker. The existing local worker does not offer a
reusable worker lifecycle or safe control over its background task.

The related `django-queues` project provides namespaced queue backends,
including Redis, together with a generic asynchronous worker API. It is a
Django-configured service library: named queues are defined in `QUEUES`,
initialized during app setup, and executed separately by `manage.py runqueues`.

## Decision

The projects will be split into two layers:

1. `django-queues` will be the generic queue and worker layer. It will provide
   named queue namespaces, generated identifiers for enqueued items, queue-item
   lifecycle metadata, and an asynchronous worker that dispatches queued items
   until it is cancelled.
2. `django-redis-tasks` will be a Django 6 task backend. It will depend on
   `django-queues` for queueing and worker lifecycle, and will translate Django
   task payloads and results to and from that generic layer.

Redis workers provide **at-least-once delivery**. A worker claims an entry with
a lease, atomically records it as running only while it owns that claim, and
atomically settles the terminal result with claim release. Expired claims are
automatically recovered to the queued state. A worker crash can therefore cause
an entry to execute again, but cannot silently discard in-flight work; handlers
must be idempotent where duplicate side effects matter.

`django-queues` remains useful independently of Django tasks: application code
can enqueue generic dictionary payloads and run independent consumers.

Both projects will require Python 3.14 or later. Queue item identifiers will be
generated by the queue using UUID version 7 and returned by enqueue operations.

For Redis-backed queues, queue lifecycle timestamps are authoritative Redis time,
not each worker's wall clock. Each process may cache a Redis-time-to-monotonic-
clock calibration for at most 600 seconds and calculate intermediate timestamps
from the monotonic clock. Non-Redis queues may document local UTC as their
fallback clock source.

## Consequences

- The in-package `redis_tasks.runqueue` runner will be removed or replaced by
  the `django-queues` worker API rather than evolved independently.
- Django application startup validates and initializes queue services but does
  not start a worker; `manage.py runqueues` owns worker lifecycle externally.
- `django-redis-tasks` will target `django.tasks` from Django 6 and will remove
  its dependency on the external `django_tasks` package.
- The generic queue API must define durable item metadata and worker lifecycle
  before the Django task adapter is implemented.
- The concrete queue-entry representation, result schema, and `BaseQueue`
  extensions are intentionally deferred to the next ADR.
- Redis-backed task handlers inherit django-queues' claim lease and automatic
  recovery behavior; this package records dispatch attempts but does not add a
  separate retry policy.
